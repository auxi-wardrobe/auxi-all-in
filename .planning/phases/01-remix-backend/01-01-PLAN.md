# Phase 1 Plan: Remix Backend

## Goal

Land a production-ready `POST /api/v05/recommendation/next` endpoint, backed by a Redis-stored session that cycles through 4 variation axes (SILHOUETTE → LAYERING → COLOR → NEW_ANCHOR), enforces anchor-pin and single-layer-swap invariants as hard-fails, and meets p95 < 250ms under 1-user load. PR open by EOD 2026-05-09 and mergeable by 2026-05-10 (Cycle 10 close).

## Out of Scope

Explicit guardrails to keep the plan small enough to ship in 2 days:

- **Mobile wiring** — Phase 3
- **Telemetry events** (Mixpanel emission) — backend only adds `trace.variation_axis` to response; mobile fires the events
- **V05 onboarding API** (ONBD-01..03) — Phase 4
- **CORS / JWT secret hardening** — Phase 2 (FOUND-04)
- **Maestro E2E** — Phase 5 (LAUNCH-01)
- **Concurrent / multi-user load testing** — single-user p95 only per REMIX-BE-08
- **LLM narration on NEW_ANCHOR** — explicit Phase 2 stretch in PRD
- **Color-pair learning** (V05 spec §15.7) — Phase 3+

### Task 1.3 — Redis session manager scaffold

**Wave:** 1
**Estimated:** 60 min
**Covers:** REMIX-BE-02 (foundation)
**Type:** plain

**Goal:** Create `RecommendationSessionV05` class — Redis-backed session for tracking outfit variation state across `/next` calls. **Skeleton only** in this task; axis-handler dispatch lands in Wave 3.

**Files touched:**
- NEW: `wardrobe-backend/utils/recommendation_session_v05.py`
- READ: `wardrobe-backend/utils/recommendation_session.py:120-333` (V2 reference)
- READ: `wardrobe-backend/utils/redis_client.py` (existing client; if missing, create minimal wrapper using `redis` package + settings)

**Acceptance:**
- Class `RecommendationSessionV05` with methods:
  - `create(initial_outfit, anchor_id, style_signals) -> session_id` — generates uuid, SETEX with TTL 1800
  - `load(session_id) -> Optional[dict]` — GET; returns None on miss or expiry
  - `advance(session_id, current_outfit_hash, force_axis=None) -> tuple[next_axis, current_state]`:
    - **If `force_axis is None`**: increments `variation_stage` with wraparound `1 → 2 → 3 → 4 → 1` (after stage 4, restart at 1). Returns next axis matching the new stage.
    - **If `force_axis is not None`**: returns `force_axis` immediately WITHOUT incrementing `variation_stage` (forced calls don't advance the auto-cycle).
    - In both cases: returns the stored state dict so the caller can read seen_item_ids, anchor_id, etc. Does NOT yet compute the swap — Wave 3 handlers do that.
  - `mark_seen(session_id, item_ids) -> None` — adds `item_ids` to `seen_item_ids` set. **Called by service after every successful handler dispatch, including forced-axis calls.** Items swapped during forced-axis calls are still tracked to prevent repeats in subsequent auto-cycle taps.
- Key format: `v05_recsess:{uuid}` (locked from CONTEXT.md)
- Stored fields exactly: `current_outfit, variation_stage (1-4), seen_item_ids (set), anchor_id, style_signals`
- Session expiry: load() returns None on TTL elapsed (Redis behavior, no extra logic)
- Type hints, docstring on each public method

**Verify:**

### Task 4.0 — Service layer method `recommendation_service.next_recommendation()` ⚠️ FIRST IN WAVE 4

**Wave:** 4 (must complete before 4.1, 4.2, 4.3 start — service is the seam between route and engine)
**Estimated:** 45 min
**Covers:** REMIX-BE-01, REMIX-BE-02 (architectural seam — service-repository pattern enforcement)
**Type:** plain

**Goal:** Create the service-layer method that the route delegates to. Sits between router (HTTP shape) and engine (variation logic). Without this, Task 4.1 has nowhere to delegate — the plan would either skip the pattern or encode it implicitly.

**Files touched:**
- EDIT: `wardrobe-backend/services/recommendation_service.py` — add `next_recommendation` method
- READ: existing service methods (e.g., `build_recommendation`) for naming + signature conventions

**Acceptance:**
- Method signature: `def next_recommendation(request: NextRecommendationRequest, db: Session) -> NextRecommendationResponse`
- Loads session via `RecommendationSessionV05.load(request.session_id)` — `None` → raise `SessionNotFoundError` (caller maps to HTTP 404)
- Validates `request.current_outfit_hash` against stored `current_outfit` hash — mismatch → raise `OutfitDriftError` (caller maps to HTTP 422)
- Calls `RecommendationSessionV05.advance(session_id, current_outfit_hash, force_axis=request.force_variation_axis)` to get `(next_axis, current_state)`
- **Dispatch table** (string → handler, fixed mapping):
  ```
  AXIS_HANDLERS = {
      "SILHOUETTE": engine_v05_variation.silhouette_swap,
      "LAYERING": engine_v05_variation.layering_swap,
      "COLOR": engine_v05_variation.color_swap,
      "NEW_ANCHOR": engine_v05_variation.new_anchor_swap,
  }
  ```
  If `next_axis` not in table → `ValueError` (caught by router, returns 500 + error code).
- Calls handler with `(current_outfit, pool, seen_item_ids, rejected_items, db)` and receives new outfit
- Calls `mark_seen(session_id, swapped_item_ids)` after handler returns — extracts changed item ids by diffing new outfit vs current_outfit
- Returns `NextRecommendationResponse` with new outfit + `trace.variation_axis = next_axis`
- Type hints on signature, docstring describing the dispatch behavior + error mapping
