Auxi Backend — Architecture & Schema

fastapi · postgres · redis · gemini / openai · railway  —  system map as deployed · 2026-06-30

The backend is a FastAPI monolith fronting two clients — the Auxi React Native app over /api/* and the internal wardrobe-admin SPA over /api/admin — backed by PostgreSQL (SQLAlchemy + Alembic) and Redis. Heavy AI work never runs in the request path: the web tier enqueues jobs to Redis, and two long-running worker services (ai_worker, notification_worker) drain those queues out-of-band.

Everything runs on Railway from a single Docker image — the web process plus the workers are separate service instances of the same codebase. An Alembic upgrade head runs as a Railway pre-deploy step, so the schema migrates before new code serves traffic.

02 · Async pipeline

Virtual try-on render — enqueue & poll

The canonical async path. The web tier returns 202 immediately and a job_id; ai_worker does the slow provider call off the request thread; the client polls for the result. Wardrobe-item AI extraction (ai_metadata) and body-shape generation follow the same enqueue → worker → S3 → DB shape.

03 · External integrations

Eight third-party services

Each integration is wired through a dedicated client/service module and gated by env vars — missing config degrades gracefully (e.g. email driver falls back to noop, Sentry disables itself).

Google Gemini

Multimodal try-on fallback + extraction fallback; recommendation judge (gemini-2.0-flash); chat agent LLM.

OpenAI

gpt-image-1 primary try-on render; gpt-4o-mini for body-photo person guard, item extraction & LLM-3 picker.

Alternate virtual try-on provider (kolors-virtual-try-on) — fallback when OpenAI render fails.

env: KLING_API_KEY · KLING_API_BASE
S3 / Cloudflare R2

Persistent object store — wardrobe images, body photos, try-on composites. Presigned URLs via CDN domain.

env: S3_BUCKET · S3_ENDPOINT_URL · S3_PUBLIC_DOMAIN
Firebase FCM

Push delivery — driven by notification_worker against registered device tokens.

env: FIREBASE_CREDENTIALS_JSON

Weather context for climate-aware recommendations. Cached ~4h (stale 12h), proxied via /api/weather.

04 · API surface

Public /api/* router groups

05 · Background workers

Two Redis-backed consumers

ai_worker

Drains ai_processing_queue (BRPOP). Dispatches by job type to the AI services and writes results back to S3 + Postgres.

  • ai_metadata wardrobe item extraction + background removal
  • tryon_render gpt-image-1 → Kling/Gemini fallback
  • body_shape_generation self-visualization render
notification_worker

Drains notification_queue + runs an in-process APScheduler that produces daily-reminder / planned-outfit jobs per user timezone.

  • Loads device tokens → FCM send → writes notification_deliveries
  • Retry 3× with exponential backoff (max 30s)
  • Also: V05 session pools cached in Redis (TTL ~1h, diversity signatures)
06 · Data model

Database schema — 24 tables, by domain

All identifiers are UUID strings. users is the hub — almost every table carries a user_id. Split into three views for readability; each Mermaid pane zooms & pans independently. JSON columns (canvas layouts, scheduled outfits, context snapshots) are mobile-owned blobs the backend stores verbatim.

Four analytics / config tables stand apart (weak or no FK edges): v05_pool_insufficient_events & v05_outfit_eval_scores (eval telemetry, JSONB GIN-indexed), algorithm_configs (DRAFT/ACTIVE/ARCHIVED engine params), and app_feedback (nullable user). v05_* signal tables reference user_id as an un-enforced logical key, not a DB foreign key.
