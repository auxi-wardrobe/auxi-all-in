# try_another — Cross-Repo End-to-End Flow Map

> Generated by `map-tryanother-flow` workflow (5 explorers + 1 synthesizer) · 2026-05-29
> Scope: auxi (RN mobile) + wardrobe-backend (FastAPI). Line numbers verified at workflow run-time; re-anchor before editing.

## 1. Summary

`try_another` is the V05 "show me a different outfit" primitive. On the mobile side, a user gesture (swipe, "Show another" tap, or background prefetch) in `HomeScreen.tsx` drives a TanStack mutation (`buildViaV05`) into the `recommendV05` service façade (`auxi/src/services/v05Api.ts:644`), which routes the *first* call of a dressing session to `POST /api/v05/recommendation/build` and *every subsequent* call to `POST /api/v05/recommendation/try_another` using a module-scoped cached `session_id` + `current_outfit_hash`. The backend handler (`wardrobe-backend/routers/v05_recommendation.py:93`) rate-limits + authenticates, then `V05TryAnotherService.try_another` (`services/v05_try_another_service.py:143`) takes a per-session Redis SETNX lock and tries to serve a *cheap* variation straight from the session's Redis pool (axis-distance scored). If the pool is exhausted, it falls through to a Phase-4 recompose: one `V05RecommendationEngine.build()` call in a thread pool (8s guard) that, when LLM-3 is enabled, surfaces 10–20 widened candidates for `V05LLM3Service.pick_with_reasoning()` (gpt-4o-mini, 3s guard) to select the best variation + fresh reasoning — degrading silently to the engine's rule-based primary pick on any failure. The result (one outfit + `cycled`/`wardrobe_gap` sustainability flags) flows back, where `recommendV05` transparently handles `410`/`422` session-reset, `429` lock-backoff, and `HomeScreen` appends the deduped outfit to its swipe carousel.

## 5. Pool Sustain Logic

**Depletion detection.** `_select_from_pool` (`services/v05_try_another_service.py:187`, scorer at `:385`) filters the Redis `pool[]` by `seen` hashes + current + `pinned_item_id` + (optional) axis hard-filter, scores survivors, returns the max — or `None` when nothing survives. `candidate is None` is the *sole* depletion trigger; there is no proactive rebuild.

**Replenish (recompose) vs cycle decision.**
- **Replenish:** On `None`, `_recompose` runs *one* `engine.build()` (8s thread-pool guard) with `force_axis` + `exclude_hashes` (all seen) + anchor rolling-window excludes. Success → outfit appended to `pool` (FIFO, oldest evicted at cap 10) + `seen`, returned with `fallback=False`. This is the sustainability fix (260527, `v05_tryanother_sustain_backend.md`): the pool *grows* via recompose rather than freezing.
- **Cycle (`cycled=true`):** When uniques are genuinely exhausted but a *real* outfit can still be re-served (controlled re-serve), the backend signals `cycled` so the client renders the outfit with a subtle "seen all" hint instead of a dead-end. Mobile reads this from the top-level `cycled` field (authoritative) or the `variations_cycled` flag (`v05Api.ts:682`).
- **Terminal gap (`wardrobe_gap=true`):** Engine raises `WardrobeGapError` → flag `wardrobe_gap_<reason>` + top-level `wardrobe_gap=True` + `outfit=None`. No auto-rebuild; mobile shows add-items CTA.

**`pool_insufficient` / `recompose_pool_insufficient`.** When recompose's `engine.build()` raises `PoolInsufficientError` — i.e., after L1 climate/occasion/gender filtering the L2 anchor pool yields fewer composable candidates than `count=1` — the service returns `None` with flag `recompose_pool_insufficient` (`services/v05_try_another_service.py:522`). It can originate two ways: (1) L2 produces too few candidates before compose; (2) the post-L5 `force_axis` filter empties the pool *and* the pre-filter pool was already `< count` (otherwise it gracefully restores + tags `axis_relaxed=true` at `engine_v05.py:842`). This flag rolls into the `_fallback_response` (`outfit=None, fallback=True`); per the 260527 sustain fix it should be a rarer terminal than a transient — mobile surfaces it via the bubble-to-`onError`/`wardrobe_gap` paths.

**Mobile-side sustain guards.** `inFlightCountRef` gates concurrent calls; `poolDepletedRef` (set on `addedCount==0`) blocks swipe re-fire spam (A2 fix 260526); `fetchGenerationRef` drops stale results after a session reset (mode change / refine submit).

## 7. Open Questions / Drift Risks

1. **`cycled` not in backend schema (highest-priority drift).** Mobile (`v05Api.ts:380`/`:682`) reads a top-level `TryAnotherResponse.cycled` boolean and treats it as authoritative, but **no explorer found `cycled` declared in `schemas/v05_try_another.py:73`** — the backend response schema lists only `fallback`/`fallback_flags`/`wardrobe_gap`. Mobile's fallback derivation from `fallback_flags.includes('variations_cycled')` works, but the top-level field may be silently dropped by Pydantic if not declared. **Verify the backend actually emits `cycled` (and `variations_cycled` flag) before relying on it** — this is the `v05_tryanother_sustain_backend.md` field that "needs tech-lead + auxi sync."

2. **`style_feedback` type mismatch.** Mobile sends `style_feedback: string` (`v05Api.ts:365`). Backend schema is reported as `Optional[str]` (`schemas/...:56`) by one explorer but the service signature is described as `Optional[Dict[str, Any]]` (service line 146) by another. If the engine/scorer expects a dict but mobile sends a plain string, the `0.5·style_feedback_fit` scoring term may silently no-op. **Confirm the canonical type in the schema vs the scorer's expectation.**

3. **`mode` is a no-op in MVP engine.** Per the swipe-pipeline explorer (AU-221), `mode` is threaded end-to-end but not wired into L4 mood scoring yet; mode change triggers only a lazy `resetV05Session` (`HomeScreen.tsx:929`). The field is in-contract but behaviorally inert — don't assume mode actually changes recommendations until AU-221 lands.

4. **`recompose_pool_insufficient` two-origin ambiguity.** The flag is emitted from `services/v05_try_another_service.py:522` but originates from *either* L2 under-production *or* a post-`force_axis` empty-and-already-small pool (`engine_v05.py:842`). Trace does not currently distinguish the two origins, making it hard to tell a genuinely-tiny-wardrobe from an axis-over-constraint at the telemetry level.

5. **Contract authority pending review.** `wardrobe-backend/docs/v05-try-another-mobile-contract.md` is the cited source of truth, but AU-248 notes it is "pending tech-lead review on backend PRs #41 + #42." Treat the contract as not-yet-frozen.

6. **Router line-number disagreement across explorers** (`try_another` handler reported at line 93, 100, and "1"; dispatch at 129 vs 135). Cosmetic, but indicates the explorers read slightly different revisions of `routers/v05_recommendation.py` — re-anchor exact lines before any code edit.

7. **Axis-cycle order mismatch in docs.** One explorer reports the cycle as `SILHOUETTE→LAYERING→COLOR→FOOTWEAR→ACCESSORY` (seen%5), another lists the enum order `SILHOUETTE, COLOR, LAYERING, FOOTWEAR, ACCESSORY`. The *cycle* order (`_AXIS_CYCLE`) and the *enum declaration* order differ — confirm `_pick_axis` uses the intended sequence.

8. **`__gen` generation guard is mobile-internal** — never sent over the wire (`HomeScreen.tsx:174`). Stale-prefetch drops rely entirely on client refs (`fetchGenerationRef`); a server-side session reset that the client doesn't observe could still surface a stale outfit. Not traced end-to-end.
